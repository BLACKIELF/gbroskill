# GBro 文章储存规范

适用于当前任务已要求的 X、小红书、微博和公众号稿件，以及用户明确要求归档的网站内容、客户资料和推文。用户要求写一版、改全文或完整文章预览时，本地保存是当前文章的交付步骤；不能只把正文贴在聊天里。仅讨论、点评、给几个标题或改一句话时不另建作品。用户明确要求「只在聊天展示、不保存」时遵从，并标明未落盘。

该约定只覆盖当前作品、用户指定资料及其知识笔记、必要清单、素材和派生预览，不授权修改其他文件、迁移旧作品、同步插件、上传、发布或写长期记忆。

## 先选唯一目录

依次采用当前用户指定的文件或目录、这件作品已有的权威目录、默认产出根目录。用户已经指定时不再另建一份。路径指向临时目录或不可写位置时，先说明问题，再确定持久交付位置，不静默改存其他根目录。

新作品先按 [general-collaboration-habits 的 File Placement](../../general-collaboration-habits/SKILL.md#file-placement) 与所属项目的现行规则确定落点。本机 AgentHub 项目的 Codex 文件按项目规则存入 `10-projects/<年份>/<项目>/work/`；已有作品继续使用原目录。`Documents/Codex/` 与 `AgentHub/Codex/` 只作历史查找线索，不再作为新作品的默认根目录。目录名沿用项目约定；没有约定时用 `YYYYMMDD-note-主题`。补平台、修订或跨天续写仍归同一作品，不因日期变化搬家。

写前检查目标文件和同主题作品清单。文件存在且内容相同就复用；内容不同时，先确认它是本轮未交付草稿还是历史版本，再按下节处理，不覆盖用户原稿或已交付版本。出现两个疑似权威副本时，只比较相关正文、版本与清单，无法确认才问用户一次，不凭修改时间挑「最新的」。

用户要求把资料整理、归位或移动到已经明确的位置时，直接移动现有文件，不另建成品副本、镜像目录或整套备份。当前文件已经位于正确位置就复用。移动前核对源文件、目标冲突和已有引用；内容一致的重复文件按本次授权合并到目标，内容不一致则保留并区分版本。移动后核对大小或校验值、更新当前清单及知识笔记链接；历史回执不改写，用移动记录保留原路径与现路径的对应关系。新下载与新生成的正式材料直接写入所属作品目录。

## 文件命名与版本

正文文件名统一为 `YYYYMMDD-note-主题-平台-语言-MMDDvN.md`。日期为该版本的交付日期；平台用 `X`、`小红书`、`微博`、`公众号`，语言用 `zh-CN`、`en` 等明确标识。短主题保持稳定，不随每次标题修改而更名。

`MMDDvN` 是本作品当天的内容版本，与软件版本、Skill 版本分开。写前查这件作品已有编号，同日递增，跨天使用当天日期。已经在聊天中命名的版本落盘时沿用原编号；编号已被不同内容占用时先解决冲突，不覆盖。

同轮多平台稿件共用版本号；只改其中一个平台时，仅为该平台新建版本，清单保留其他平台仍在使用的旧版。未交付的本轮草稿可继续修改；已交给用户、已确认或已发布的文件保持不变，后续改动另存新版本。内容无变化不增加版本，也不用「最终版」「最终修改版」替代编号。

示例只展示有实际内容的两个平台，不要求每次创建四份空稿。

```text
20260908-note-工具使用经验/
├── 作品清单.md
├── 20260908-note-工具使用经验-微博-zh-CN-0908v1.md
├── 20260908-note-工具使用经验-公众号-zh-CN-0908v1.md
├── assets/      有图片时创建
└── previews/    需要预览时创建
```

## 正文与配套内容分开

每个平台、每种语言有独立 Markdown 正文源，正文文件只放该平台要发布的标题、正文、图注、链接和必要代码块，不混入内部审稿意见、交付说明、账号信息或发布状态。

用户说“定稿／定版”时，按[编辑与发布](delivery.md)先交付当前定稿文件夹入口，再通过Codex机器人发送必要的可复制文字、适用口令与按图序排列的成品图，随后处理已明确的X发布。飞书默认不附独立Markdown／Word、参考原图或资料包；用户点名才发送，ZIP仍按既有排除规则处理。作品清单不能代替实际发送与回读。

微博引导语、公众号摘要、备选标题放进作品清单的独立字段；较长的配套回复、安装口令或制作提示词按同一命名规则单独存文件，再由清单引用。文章本身需要向读者展示的操作口令保留在正文里，不能为拆文件而删掉关键步骤。

默认保存 Markdown 正文源、必要素材和作品清单，不主动生成或重复复制 ZIP。只有用户明确要求打包时才生成 ZIP；已有符合本次稿件版本与交付要求的 ZIP 就复用，不反复另存。已有 ZIP 不因本规则而删除或覆盖。

只在发布、排版或用户交付确实需要时生成 `.txt`、`.html` 或文档。这些副本都从清单指定的 Markdown 源生成，不能手动维护两套正文。源稿变化后重新生成受影响的预览或发布用副本；未更新的预览在清单标为过期，不能当成当前稿交付。

## 一份作品清单

优先复用已有能承担相同职责的清单，不另建竞争索引；新作品用 `作品清单.md`。至少记录以下信息。

清单开头用一张总表指向各平台当前可用文件，包含平台/语言、内容版本、正文与评论文件、配图及顺序、飞书交付入口、公开发布状态/链接。清单自身的管理版本与各平台内容版本分开；仅整理目录和记录，不给未改动的正文或图片虚增版本。阻塞项写明原因与下一步，已发送、已发布和未完成部分分别记录。

- 作品主题、目录、创建日期和用户要求的平台范围。
- 各平台与语言的当前正文相对路径、版本、标题，以及适用的引导语或摘要。
- 本版相较上一版的具体差异、旧版文件位置；补存聊天稿时注明沿用哪一版，不声称已经过用户确认。
- 封面、正文图、回复图的文件与顺序，图片来源、选定基准、演示或实拍属性；当前无图就写无图，不造空文件。
- 关键事实来源及核验日期、尚待确认的事实或功能边界。只保留任务必要信息，不保存凭据、完整私密日志或无关个人信息。
- 本地内容状态、飞书交付状态、平台操作状态，以及已核验的公开链接和时间。飞书记录逐项稿件／图片的发送结果与消息 ID；四个平台和主帖、文章、回复分别记录。

本地内容区分「草稿／待确认／已确认」。平台状态区分「未发布／网页草稿已保存／已提交或审核中／已发布／失败或未核验」。只有真实证据支持时才升级对应状态；本地保存、用户认可、点击发表、公开可访问不是同一件事。发布许可仍按编辑与发布规则，不因清单有状态而额外索要或推定授权。

## 图片、临时产物与旧版

当前用户要求定稿后给出文件夹入口，交付文件夹只保留当前定稿的正文、实际需要的独立评论和全部配图。优先复用作品已有的定版目录；没有时在原作品目录内使用 `定版文件/`，按实际平台、语言及图序整理，不另建作品根目录。草稿、旧版、提示词、来源与验收记录放在交付文件夹之外，作品清单保持唯一并指向当前文件；不把整理交付解释为永久删除历史或原始素材的授权。

配图按原图相对顺序保存，原始素材与裁切、改字等派生图分开命名，不能覆盖已确认基准。已在作品目录内的图片直接复用；仍在临时目录或生图缓存中的当前任务成品，按已授权的整理要求移动到指定位置，使用相对引用，并在清单保留来源与图序。只有用户明确要求导出副本或打包时，才另外复制。

多平台共用的同一张图、视频或使用口令只保留一份正式文件，由清单关联到各平台；平台需要不同文字、尺寸或裁切时才保存派生版本并注明来源。图片从生图缓存转入作品目录后检查文件完整性；校验值可用于确认复制和发送的是同一文件，不替代内容目视。用户明确要求不做哈希时不运行图片或 PDF 哈希校验，改用文件存在性、内容对账、视觉验收与发送回读确认。

网页缓存、调试截图、临时渲染和失败候选不混入当前发布稿。临时目录可用于制作，但不能作为唯一交付位置。没有迁移要求时旧版保留原路径；用户已明确要求整理归位时，移动到本作品既定历史分类并更新引用。保留版本内容，不把整理理解成删除不同版本的授权。

沿用作品现有分类。没有分类时，按实际内容使用 `交付/` 存当前稿件与媒体，`来源/` 存必要原始材料，`qa/` 存核验、发送回执与发布记录；没有内容就不建空目录。制作提示词和历史稿置于交付区之外，并从清单链接。移动或改名之前查重和检查引用，完成后核对链接；历史发送回执保留原始记录，不伪改成新的路径。

## 本地、飞书与 Obsidian

- 本地作品目录是稿件和媒体的权威保存位置，保留当前成品、必要来源与历史版本。
- 飞书用于交付可复制文本和实际媒体，消息 ID、附件和回读结果记回本地清单；发完飞书仍要完成本地储存管理。
- 已完成的教程、说明，以及用户要求归档的已上线网站内容、客户资料和推文，按 [Obsidian 规则](../../general-collaboration-habits/SKILL.md#knowledge-notes-in-obsidian) 写入既有库。保存可复用的实质正文、方法或用法、原链接和持久项目入口；公开短配文和执行状态不能代替知识正文，调试日志不机械建笔记。只归档时不启动图文视频制作、发送或发布，不自动回填未指定的历史资料或开启监控。
- 先按主题和规范原帖 URL／ID 查重。同一主题的更新可合并入已有笔记，保留日期和用户原有内容；这不改变不同选题分别制作的约定。原作者、转述者、主帖、引用、回复和延伸文章分别标记，采集到的评论不算用户另外提供的新任务；缺原文或原链接时注明缺口，不补猜。公开稿的删链、去署名规则不套到知识笔记。
- 网站内容注明正式网址、资料时点和实际核验范围，区分线上页面与本地候选；客户资料分清原话、用户转述、确认稿和制作建议；推文分清作者主张、个人经验与本机实测。保留所需附件的持久入口，大视频和完整制作包优先引用原项目，避免另造权威副本。
- 写后回读正文、内部链接和附件入口，在已有作品清单记录对应笔记路径及归档状态；纯资料归档复用现有主题索引，不为每篇新造作品清单。笔记文件保存并验证后才报已归档，未同步部分明确列出。

## Skill 素材库与分类打包

用户要收集可复用 Skill、评论口令或未来商品素材时，在现有作品资料区维护一份索引，按用途分类；优先满足本轮指定数量与场景，PPT／演示设计、图文视觉可独立成类。以规范仓库名和具体 Skill 路径去重，不用星数、中文译名或多个精选榜重复计数。索引保留仓库 URL、采集时间、固定 commit、文件哈希、具体用途、适用 Agent 路径、运行依赖、安装口令与验证状态，标明 Skill、工具、MCP 或目录。

用户要求下载时，轻量 Markdown 与必要参考文件可直接归档；用户要求打包时再生成对应 ZIP。研究摘录包与可安装 Skill 包分别标明：只有 README 或 SKILL.md 摘录，不能冒称完整安装包；涉及 scripts、references、assets、包配置或外部运行环境时保留实际必需文件，缺失项在中文使用说明中说明。只下载不等于安装，不向当前 Agent 的技能目录自动写入。每个包附中文使用／安装说明；压缩包列明版本、文件清单和哈希，并验证能正常读取。

用户提出未来售卖或再分发时，逐项回查上游 LICENSE、NOTICE 和文件级条款；“公开可读”或“source available”不能直接判断为可转售。可纳入的源码保留要求的许可和版权文件；限制分发或许可不明的项目只保存内部研究记录与官方获取路径，不混入宣称可分发的源码包。公开稿件默认不写作者的约定，不扩大成删除软件分发必须保留的版权信息；用户已授权的输入素材与另行搜集的仓库分别判断。不要把资料整理、许可文本核对或成功下载写成已在 Muse 实测或已经具备售卖资格。

整理已有文件前检查引用，采用移动并更新索引，避免另建平行副本。正式源文件保持一份；用户明确授权的交付 ZIP 是派生包，不替代来源档案。AiGoodBro 品牌预设已明确要求 ZIP 不发飞书：压缩包只保存在本地，飞书发送正文、说明文档和当前指定素材；只有后续明确改变这一要求时才发送 ZIP。先交付本轮筛选结果，再继续已授权的扩展收集，不为凑库数量拖延用户要用的内容。

## 交付前做最小验收

1. 从作品清单读回当前文件，确认本轮所需平台与语言齐全、路径存在且正文非空。
2. 逐段核对落盘正文与本轮交付稿；除 Markdown 表现形式外，标题、数字、口令和顺序一致，没有截断或混入内部说明。
3. 有图片或预览时，核对实际引用、图序和受影响的呈现；源稿与派生文件一致，旧图或旧版预览未被误用。
4. 发布状态只写已取得的证据；失败或不确定时保留当前稿和缺口，不重新创建整件作品或重发已成功部分。
5. 回复用户本轮版本、变化、作品清单或成品目录的可点击入口，并附可复制的文字版绝对路径；说明实际发布状态。未能持久保存时明确写「正文已给出，文件未保存」，不能宣称储存完成。

只更新储存规范时，不顺带补存、迁移或重写历史文章。用户要求补存时，先复用原目录和聊天中已经交付的正文；正文无法完整恢复就说明缺口，不能凭摘要重写后声称是原稿。
