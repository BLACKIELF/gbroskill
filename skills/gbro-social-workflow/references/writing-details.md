# 长文、真实案例与工具教程细则

只在当前稿需要真实案例复盘、功能解释、长文章、跨 Agent 教程或英文稿时读取相关小节。简短平台稿优先遵守[内容结构](content.md)，所有公开指令遵守[渠道边界](delivery.md#各渠道的链接与行动引导)。

## 从记录写成真实案例

材料零散时，先还原「遇到什么问题 → 实际怎样处理 → 得到什么经验 → 哪些产品改动已验证」。让读者的问题决定取舍，不把开发日志、修改清单或测试数量照搬成文章。用户指定的项目泛称、必须出现的功能与优先级单独锁定，避免改稿时又泄露原项目名或删掉重点。

- 新闻钩子先核验一手来源的发布时间、事件时间、适用人群和机制；临时赠送、手动兑换、周期重置不能混写。没有证据不写「所有账号都自动重置」；新闻与个人遭遇分别叙述。
- 运行案例记录统计时段、覆盖范围和来源，区分任务、尝试、重试与子任务。Token 总量说明缓存口径，不直接等同费用、有效产出或效率提升；失败任务的消耗不能当成成功成果。无法核实模型选择器或实际输出时，不把某个具体模型署名为方案作者。
- 对涉及的软件功能，建立简短的内部对照：读者问题、当前入口、按钮真实动作、内置或外部能力、前置条件、证据、可公开状态。名称像「优先调度」，实际只保存偏好时，只能按真实动作介绍。
- 断点续做等另附口令与 App 功能分开。给个人单账号用户的模板应保存目标、已完成与未完成、文件位置、验证结果和下一步；恢复前读取检查点并核对实际文件状态。没有验证时不承诺后台自动续跑、自动兑换额度或绝不丢进度。
- 标题可以有钩子，但正文必须兑现。要突出某个机制时，把它放在问题之后较早解释，不把关键使用条件藏到末尾。

### 翻车复盘与设计对比

用户给出对话截图并要求调取当时素材时，先用可见的任务名、项目名、原话和时间定位相关任务。通过任务读取工具及必要的本地记录，找出设计稿、对应轮次的代码渲染图与追问答复；对话里的缩略图只用于定位，成品使用调取到的原始文件。内部记录任务、轮次或时间、文件路径及图片性质，不扫描无关对话。缺少原件时如实标明，不能拿修复后或最近生成的图替代翻车当时的图。

- **模型与档位按当时记录核对。** 核对实际执行轮次的模型和推理档位，不以当前任务设置或模型菜单选中项倒推历史。“Max”与“最高档”分别核实；记录只证明 Max 时写 Max 档，未核实当时可选上限就不自行加“最高”。
- **分清素材阶段。** 设计稿、真实代码渲染、合成数据预览和最终安装版分别表述。构建通过只证明相应构建成功，不能据此写成视觉验收通过；模型承认“不一样”是对话证据，具体差异仍要看原图。
- **比较保留条件。** 明确两图的窗口尺寸、数据、页面和控件状态是否一致。不同演示数据造成的账号数量、卡片条数或内容长度变化，不能直接算作布局错误。条件不一致时只写可见差异并说明限制；要判断还原程度，需同数据、同尺寸、同状态截图核对。
- **结论限定到本次任务。** 标题可以写具体的翻车，正文说明发生在哪个开发阶段、偏差在哪里；不把单次结果概括成模型整体能力差或最终产品失败。自然收尾到可操作的验收方法：锁定设计与样例数据、运行截图、逐区比对、有偏差先修再复验。写复盘本身不触发项目改码、安装或补跑测试。

## 微博与微信公众号文章

同一份材料先核验，再按不同阅读场景取舍。只补这两个平台时，保留已确认的 X 和小红书，不重新发布旧稿；正文引用相对时间或本机安装状态时，按新的成稿时间更新，不改写历史发布记录。

| 平台 | 应交付与写法 |
| --- | --- |
| 微博文章 | 标题、完整文章、必要配图，另附用于发布该文章的简短微博引导语。开头尽早讲事件、读者的麻烦和作者判断，细节围绕最有用的方法展开；用户说「文章」时不擅自缩成普通短微博。 |
| 微信公众号 | 标题、摘要、完整正文、封面与正文图对应关系。用真实过程、失败、改动和操作方法支撑长文，材料够才展开；适量小标题帮助定位，口令用可单独复制的完整文本。文章应独立读懂，不要求先看 X 或私信才能理解关键步骤。 |

篇幅服从材料与当前编辑器，不把小红书少于 1000 字的默认套到长文章。话题、链接、封面裁切、摘要和署名按平台与用户要求分别处理，不假定四个平台规则一样；也不把尚未核验的字数上限、外链能力或群发次数固化成永久规则。

引用公开文章时，先提炼事实与可采纳的观点，再结合用户自己的材料形成文章。按AiGoodBro 品牌预设已授权素材约定，原作者姓名、来源网址和授权说明默认保存在内部，公开稿默认不写原作者；用户明确要求保留或人物身份本身是内容中心时，按主入口规则保留必要姓名和关系；不把别人的亲历、截图或判断改成用户亲历，也不把改写误当成对素材拥有全部权利。

## 功能怎么写详细

对重要功能，在内部回答以下问题，再组织成自然段落，不必把每段都排成同一张清单。

| 读者的问题 | 应补的细节 |
| --- | --- |
| 它解决什么麻烦？ | 真实场景与需要手动完成的动作。 |
| 从哪里使用？ | 页面、卡片、按钮、开关或入口。 |
| 什么时候发生？ | 手动还是自动，触发条件，默认是否开启。 |
| 会做什么？ | 动作、对象、输出或后续状态。 |
| 需要准备什么？ | 支持平台、登录、依赖、网络与必要配置。 |
| 有什么边界？ | 消耗、失败条件、未支持能力和当前发布状态。 |

先写用户明确强调的功能，再写相关细节，不按设置页按钮的出现顺序机械罗列。次要外观设置可以合并为一段，主要使用流程值得配图单独解释。

涉及当前产品能力时，先看本轮可用代码、文档与界面，再按需要查官方来源。重要断言保留来源与时间供内部核对，不把调试日志堆进成稿。遇到冲突，以新证据修稿；无法确认时缩窄措辞或标清状态，不靠「应该支持」补齐卖点。

## 工具教程的可复制内容

当正文或封面承诺「安装口令＋触发词＋调用技巧」时，三项都要完整交付，让读者复制后有明确的第一步。

用户要跨 Agent Skill 或可持续选题的素材库时，结合中英文关键词（如“必装 skill”“实用技能”“must-have agent skills”“best agent skills”）搜索 X 用例与 GitHub 精选目录，再回到项目 README、实际 Skill 文件和安装文档核对。互动量与 stars 记录采集时间，仅作发现线索；按同一项目、功能和使用场景去重。分清 Skill、工具、MCP、Agent 入口和资源目录，目录不能当作一个可整包安装且全部验证过的 Skill。每条保留具体用途、一句话安装或调用口令、依赖、事实来源和适合的内容切口；来源内部归档，评论正文保持纯文字。

“跨 Agent 通用”要按实际执行路径判断：例如 Muse 云电脑可作为宿主，在其中安装或调用支持 Skill 的 Agent，再由该 Agent 使用技能；不能仅因安装器的原生支持表没有 Muse 就排除这条路径。项目有 Muse 原生安装说明时优先核对该说明。分别检查 Skill 格式、宿主 Agent、运行依赖和账号条件；没有在目标环境执行过的安装或功能，不写成亲测成功。没有核实的统一命令不编造，也不把内置 Skill 的免安装说明扩大成第三方工具无法安装。

- **安装口令：** 写清目标工具、可信安装来源、已有安装与配置的处理方式、当前 Agent 支持的接入方式、必要准备和完成后的核验；需要登录时交给读者用户操作。只给仓库名称不能代替承诺的完整口令。
- **持久触发词：** 给出准确触发短语及触发后要做的事。若承诺以后仍能使用，应要求执行安装的 Agent 写入其实际支持的持久规则、核对并回报保存位置；不能把一句聊天答应当作已经保存的规则。
- **调用模板：** 按真实用途给出可单独复制的请求，包含必要输入、要作的判断与期望结果。Oracle 案例是方案比较、卡点排查、项目审查、资料总结四类；其他工具按实际用途选择，不强凑四个。

同一作品各平台引用同一套已确认功能与模板，按渠道适配安装来源的表达；小红书、公众号均无网址，涉及的每个仓库另交一句安装或使用评论，按[渠道规则](delivery.md#各渠道的链接与行动引导)处理。英文触发词可以自然改写，但触发后的动作、条件和授权范围须一致，不能译成另一套工作流。只是在教程中提供口令，不等于本轮已经执行安装或写入规则。

## 面向海外的英文稿

- 保留主要问题、功能优先级、操作细节和实际边界，按自然英文重写句子与标题。品牌名、模型名和代码标识保持一致。
- 首次出现本地或特有概念时说明实际作用，不照搬另一项目的定义。
- 对海外读者补充真正影响使用的内容，例如系统要求、英文界面覆盖范围、安装入口、额外依赖和国际版服务名称。
- 用户只要求英文正文、未限定截图语言时，可以保留中文截图并提供英文图注，不据此宣称产品已全面英文支持。用户要求原生英文截图时，必须取得真实英文界面或明确标注的原生演示渲染，中文截图加英文图注不算完成；用户明确要求直接翻译截图文字时，按[界面译制规则](visuals.md#已有教程截图先判断是否直观)处理，不能把译制图冒充原生界面或实测结果。
- 逐项核对中英两版的数字、默认开关、前置条件、发布状态、图片对应关系和链接。不能翻译掉限制，也不能给英文版添加未经核验的新卖点。
- 勘误先修事实，再修语法、用词、标点和衔接；检查图片里的英文是否与正文一致。
