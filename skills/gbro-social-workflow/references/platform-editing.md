# 平台草稿、勘误与发布细则

编辑平台已有草稿、修正已发布帖子、补缺稿或处理编辑器故障时读取。授权、去重和最终交付以[GBro 交付规则](delivery.md)为准，本页不增加平台、账号、自动重试或定时任务。

## 编辑已有草稿

- 从现有目标页面或草稿开始，核对账号、标题、语言和 URL；不要因为页面暂时空白就立即重建同名文章。
- 编辑前保留现稿文字和原图顺序用于比较。复用已有素材和成稿文件，替换指定段落时避免重建整个富文本正文而丢失图片。
- 长文本以最终 Markdown 中的可发布正文为输入源。X 富文本的 `innerText` 曾在空段间额外插入换行，直接读出后再回填会越改越空；只归一化已核实的界面表示差异，再与源稿逐段核对，不全局删除真实段落或把界面读回值直接当成新正文。
- 长文本输入后读取实际字段，检查是否缺字、多字、拼接错段或乱码。自动保存后核对实际已保存内容，不以剪贴板内容或写入调用成功代替验证。
- 附件加入或页面重渲染后，再将可见字段的全文与最终正文逐段比较，并核对已加载缩略图的数量和顺序。此前输入正确不保证当前待提交内容仍完整；不能只确认开头、结尾或某个短语存在。
- 纯文本值设置可能绕过网页保存事件；发现没有保存时换用已支持的正常输入或粘贴方式。按当前可用浏览器工具文档操作，不把特定机器上的元素编号或快捷键写死。
- 使用图片稳定标识与图注核对原图相对顺序，检查新增图与对应段落的关系。

## 缺稿改写与去重补发

用户已明确要求把当前新稿发到指定平台，并补充“没有的就改写”时，缺少平台版本是改写任务，不是停止发布的理由。先从当前作品清单定位已交付版本，再按账号、主题、语言和主帖／回复核对实际已发布内容；补平台不自动把整个历史档案加入发布队列。平台与作品范围确实不清时，先完成可确定部分，再只询问会改变范围的一项信息。

同题已有完整版本时跳过该项；只有配套回复缺失则只补回复。尚未发布且没有该平台稿时，以已核验素材独立改写，沿用同一作品目录、建立平台正文源并更新清单。保留已交付的其他平台版本，不把小红书正文直接当作所有平台的最终稿。新加入的价格、功能、条件和来源须核验；公开来源、赠送条件和语言按本次要求处理。

正文与图片逐项核验后在既有明确授权内发布，每项先保存实际链接和回读结果，再处理下一项。点击提交但结果不明时先查当前状态，不重复点发布。完成时逐项报告实际已发与未发，不用“全部完成”概括只检查过的两个主题，也不把某平台已发当成另一平台已发。

## 修改已发布帖子

- 用户提供了已发布笔记的审核截图或补充其已手动发布时，立即更新任务状态；不继续沿用“尚未发布”的旧计划新建同稿。先核对现有帖、最新正文图片及用户修改，按当前授权原位更新。只有用户明确要求才删除或另发，不把历史违规记录当作当前审核结果。
- 用户要求补充 @、勘误或修改原推文时，先使用该帖实际提供的编辑与更新功能，保留未要求改动的全文、段落和附件；不另发一条主帖代替编辑。当前账号或帖子不支持编辑时说明限制，不擅自删除重发。
- 点击更新后先读实际状态。若仍停留在旧链接，且更新已经完成，可刷新一次检查平台是否提供「新版本」链接，并沿实际链接核对最新版；不因为旧页面缓存就再次提交。
- 核对更新后的全文、提及所对应的账号链接与保留的图片。平台若生成新的版本 URL，在作品清单记录最新链接及旧链接的版本关系；这属于原帖编辑，不报成新发主帖。取得结果后停止操作。

## 预览与勘误

在目标平台实际预览里检查封面比例、标题、段落间距与空白块，并核对功能、条件、版本、图注、语言和链接。小红书另核对完整正文长度；小红书、公众号均按[渠道边界](delivery.md#各渠道的链接与行动引导)核对正文、图片和配套评论无网址，仓库与独立一句话评论逐项对应。图片数量随稿件变化。

发现问题就定点修复，再核对受影响部分；没有新问题时不反复刷新或无限检查。工具不可用时可以交付本地预览，但必须说清它还不是目标平台的已保存草稿或已发布结果。

发布前确认：文字无未解决的重要勘误，图片顺序符合要求，正文与截图的发布状态一致，链接指向正确项目或文章，受众符合用户要求。

## 主帖与配套回复

按已授权的发布计划列出主帖、首条回复、各自图片与语言。用户已要求发布的配套安装说明或口令回复一并执行，不遗漏；仅正文出现「评论区见」不构成发送任意评论或私信的许可。

1. 主帖提交前，准备好承诺放到评论区的最终文字、公开链接与剩余图片，并确认其发布安排和权限。依赖项缺失或操作方式已受阻时，先不提交带此承诺的主帖；不能先发完再临时找内容。
2. 提交主帖后，记录实际公开链接，并从该帖子进入已授权回复。主帖和回复分别核对实际全文、媒体、关联对象及可观察的发布结果。
3. 主帖已成功而回复失败时，不重发主帖。保留主帖链接、待发回复与未发布图片，报告「主帖已发，回复未发」，后续只继续未完成部分。

在评论区提供的安装或续做口令应可单独复制，并写清适用对象、准备条件与需用户完成的步骤。公开指令使用软件名或公开仓库，不带本机私人路径、真实账号、密钥或内部任务内容。给出安装口令不等于代用户安装、登录或执行任务。

## 输入异常与停止条件

按钮点击或文件选择没有反馈时，先查看真实页面与窗口状态，判断是否已提交、正在加载或窗口未激活；确认本任务仍占有界面后，通过工具支持的方式激活正确窗口再操作。不要仅因一次点击调用返回成功就报告已发布，也不要未经检查连续点击提交。

若出现中文失真、正文只剩尾段、混入无关剪贴板内容、附件错位或目标账号不符，立即停止提交。核对目标后，只清理本轮写入的未提交错误内容，保留用户原有草稿与本地正确稿件，不删除已发布内容。清理是否成功也要核对；无法清理时明确告知用户，不宣称草稿已清理。

同一症状连续两次操作无进展，且用户仍要求完成时，停止原样重试，转入主动排障，不直接用“不能做”结束任务。保存准确报错、操作阶段、页面实际状态和工具版本，先查官方文档、GitHub issues／修复记录及相关X案例；默认沿用anysearch，关键结论回到维护者回复或代码。没有搜到可验证方案就明确说明，不把宣传帖或不同环境的经验当成本机修复证据。

根据证据区分参数／焦点错误、工具缺陷、版本问题和真实权限拒绝，选择最小修复或受支持的替代路径，先验证受影响步骤，再续做原任务。替代路径不能扩大原授权、绕过权限／身份／付费或完整性检查，也不能在结果不明时重复提交。用户提出Word／富文本整体复制等办法时，先核对目标编辑器是否支持，并回读全文、图片数量和顺序；粘贴调用成功不等于图文完整。

只有缺少信息、权限或人工步骤确实阻塞时，才给出具体原因、依据和一个最小协助动作；不要让用户先排障而稿件尚未准备好。保留本地成品、已发布链接及待发项目，不从头重做。用户明确叫停时立即结束控制与后续提交；持续授权不等于授权取消安全保护。

区分实际报错、工具给出的排障建议与已验证根因。例如工具建议检查文件权限，只能报告该建议，不能在未复验时宣称权限就是原因或已恢复。局部上传阻塞不耽误独立的本地改稿、飞书交付与已授权 Skill 更新；用户指定的新交付顺序优先，不将某次“飞书→微博→小红书”固化为所有任务的默认。

### BrowserSkill 与 X 的历史恢复案例

- 本机BrowserSkill 0.3.0、Chrome153上传出现`DOM.setFileInputFiles / Not allowed`。先实读扩展详情，确认“允许访问文件网址”为关闭；用户明确允许后开启，扩展随即重载并恢复连接。新会话正常上传4张图，页面回读4个媒体项。依据为[维护者说明](https://github.com/microsoft/playwright-mcp/issues/1481#issuecomment-4145954482)及本机前后验证；不采用全局关闭文件访问检查的参数，不将相同报错一律归因于权限。已有明确授权继续有效，权限范围变化才另问。
- 操作参数绑定当前观察实际返回的`tab_id`。会话默认标签发生变化时，不能把另一个标签的refs用于点击；扩展重载后旧会话失效，应重新创建并观察，不能沿用旧ID。原生窗口被其他任务切走时，协调界面使用，重新读取当前窗口；不在旧索引上继续粘贴。
- 本次X的`fill_value_mismatch`伴随contenteditable显示为空。正常粘贴后字符计数更新，但正文仍不可见；通过X界面“关闭→保存草稿→草稿中打开本稿”恢复完整文字与4图。此时才逐段比对源稿，确认邀请码、来源、媒体和受众，再发布一次。DraftJS的`innerText`空段表示可能多出换行，只归一化已确认的表示差异，不能忽略漏字或实际排版差异。粘贴、保存、发布分别验收，不以字符数替代全文核对。
- 后续补发再次遇到相同显示异常：只放弃本轮新建且未发布的异常草稿，重新打开干净编辑器后，原生粘贴可正常显示全文。可按当前草稿是否含用户原内容、已上传媒体和可恢复程度，选择保存重开或重建本轮草稿；不原样反复`fill`，不改写网页内部状态来掩盖空白。先观察焦点与实际窗口，粘贴后对照全文，再核对媒体及受众；恢复成功只证明本次路径有效，不宣称已修复浏览器或平台本身。
- 用户明确要求邀请码放最前面时，准确使用本次给定的邀请码，紧邻说明每位符合条件者可获得的奖励、兑换时限及实际入口。不要把有资格限制的奖励写成无条件到账，不将本次产品、邀请码或token数量带入其他稿件。X要求来源时公开标注来源，优先于此前其他平台的默认不署来源约定。

本例[公开结果](https://x.com/Aigoodbro/status/2102454829050118268)已核对全文、4图及实际发布时间。该记录是恢复案例，执行新任务仍读取当前工具文档和实际页面。

## 英文版引用转发

用户要求英文版用转发形式时，默认理解为 **引用转发原中文内容，并提供英文内容**。

1. 若已有完整英文文章草稿且用户要求发布全文，先完成勘误并发布英文文章，取得公开链接；若用户只要一条短英文转发，就直接在引用文案里写完整意思，不额外发一篇文章。
2. 从已确认的中文原帖选择 X 的「引用」，保留原帖卡片。普通转帖不会新增英文文案；仅粘贴原帖链接也不能冒充已完成引用转发。
3. 引用文案用自然英文说清主题和少数核心用途。已有英文全文时附上它的链接，话题保持简短相关。
4. 提交前核对引用对象、英文链接、文案、话题和目标账号。按当前编辑器限制排版，不假定所有账号都只有同一个字数上限。
5. 取得可观察的发布结果或公开帖子链接后停止操作。不能只因点击了按钮就报告发布成功；也不要在成功后顺手点赞、置顶、再转发或修改其他内容。

最终给用户发布结果与实际链接；有配套回复时分别说明。仅保存、提交失败或无法确认时，分别说明，不把这些状态统称为完成。结束时归还本次借用的标签页并关闭控制会话，不改动用户其他页面。
